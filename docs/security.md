# Security and Privacy

## User Onboarding and Authorisation Processes

Account instantiation operates via a multi-tiered server-validated lifecycle. Access rights are denied by default, binding a single user UUID to a single role and a single verified tenant organization to ensure complete multi-tenant data isolation.

### Phase 1: Institutional Tenant Provisioning
Before any user registration can occur, the Community Seed Bank (CSB) entity must be formally whitelisted.

```text
[CSB Registration Submissions] 
       │
       ▼
[Verification against National CSB Registry] 
       │
       ▼
[Admin Script Sets organization.is_verified = TRUE] 
       │
       ▼
[Tenant Active: Inbound User Sign-Ups Unlocked]
```

### Phase 2: Role-Specific Onboarding Execution

#### Track A: Seed Custodians (Mobile App Journey)
1. **Token Verification:** The user inputs a unique invitation alphanumeric code generated by their parent organization. The backend maps this token against `organisation_id`.
2. **OTP Challenge:** The user provides their phone number to trigger a 5-digit verification hash challenge via the Africa's Talking SMS API gateway.
3. **Activation:** Upon successful matching, the server constructs the user record, assigns the `seed_custodian` role dictionary, and enforces default minimum privilege parameters.

#### Track B: CSB Coordinators & GeRRI Specialists (PWA Journey)
1. **Administrative Creation:** Accounts are provisioned exclusively through backend onboarding workflows managed by system administrators.
2. **Credential Generation:** Initial access requires an explicit email mapping paired with a password string hashed using standard **bcrypt single-input salts**.
3. **Authorization:** Accounts assign to either `csb_coordinator` or `gerri_specialist` roles. 

### Phase 3: Server-Side Authorization Controls

```text
Inbound Client HTTP Request (JWT Bearer Token)
       │
       ▼
[API Token Parser Router Guard] ──(Invalid / Expired)──▶ 401 Unauthorized
       │
       ▼
[Extract User UUID + Organisation UUID]
       │
       ▼
[Role-Based Access Control Middleware Checks]
       │
       ├──▶ Custodian: Restrict to assigned Organisation UUID holdings only
       ├──▶ Coordinator: Unlocks local vault administrative mutations
       └──▶ Specialist: Deny access unless record is linked to active Support Request UUID
       │
       ▼
[Permission Granted] ──▶ Execute Business Logic ──▶ Log Transaction to Audit Table
```

### Phase 4: Token Lifespan & Session Hygiene
- **Cookie Flags:** Tokens deploy using `HttpOnly`, `Secure`, and `SameSite=Strict` browser constraints to eliminate cross-site scripting (XSS) vectors.
- **Inactivity Expiry:** Session signatures invalidate automatically following **10 minutes** of client idling.
- **Brute-Force Lockout:** Triggering **3 consecutive failed authentication checks** locks the target account profile temporarily for 5 minutes, appending an entry to `audit_record`.

## Knowledge Hub Media Lifecycles & Content Security

To securely manage binary assets (photos and short `.mp4` video entries) while preventing spatial privacy data leaks or unauthorized data extraction, uploads track through an explicit lifecycle.

### Step 1: Decentralized File Upload Handling
Media bytes are decoupled from the core database creation strings to protect transaction speed and prevent arbitrary binary execution paths.

```text
1. Mobile App queues upload payload -> 
2. Streams raw file chunks to Dedicated Media Storage -> 
3. Storage bucket returns asset URL -> 
4. API records metadata reference link inside media_file table
```

### Step 2: Perimeter Boundary Validation
The API perimeter inspects inbound files at the boundary before writing entries to disk storage blocks:
- **Magic Byte Signature Verification:** Verifies headers match allowed image/video formats (rejecting files like a `.exe` disguised with a `.mp4` name wrapper).
- **Payload Constraint Filters:** Rejects any asset exceeding strict size boundaries to mitigate storage exhaustion or Denial of Service (DoS) exploits. If validation fails, `upload_status` updates to `failed`.

### Step 3: Audited Public Sharing Workflows
Knowledge sharing items are set to **private-by-default**. Converting an entry to a public state requires executing this verification sequence:

```text
[Custodian sets entry visibility to Pending]
       │
       ▼
[WAF Rule Scans Content: Flags matching named PII or precise GPS coordinates]
       │
       ▼
[CSB Coordinator reviews automated flags + views content inside PWA]
       │
       ▼
[Coordinator signs verification checkbox -> Writes signed consent row]
       │
       ▼
[API switches status to Public -> Appends row to append-only audit trail]
```

### Step 4: Revocation & Content Withdrawal
1. The authoring organization triggers a `DELETE` or `PATCH` instruction to adjust visibility.
2. The server instantly drops the entry from the global index and marks the record `is_archived = TRUE`.
3. Short-lived signed asset destination links expire within minutes, blocking subsequent external client access requests.

## Security Architecture Overview

Security in Mbegu Link is designed around one principle: community control of seed information is an architectural requirement, not an interface setting. Seed records can contain farmer identities, collection locations and indigenous knowledge, so the system is built so that hiding something in the user interface is never the only protection — every permission is enforced on the server, before business logic runs.

The security model rests on the system's layered structure. The mobile app and the Progressive Web App (PWA) are the only two entry points, and both communicate exclusively over HTTPS with the FastAPI backend. No client ever connects to the database directly. This single rule is what makes authentication, role-based authorisation, multi-tenant isolation and audit logging enforceable in one place: the backend is the security boundary for the entire system.

The diagram shows how each layer contributes:

| Layer | Security responsibility |
|---|---|
| **Clients** (Mobile app, PWA) | Collect credentials securely, never store secrets, display errors without technical detail |
| **API layer** (FastAPI) | Authentication, role-based authorisation, input validation, rate limiting, audit writing, secure headers |

Passwords are stored only as salted bcrypt hashes and are never logged or displayed. Accounts are temporarily locked after three repeated failed login attempts, password reset uses single-use email codes, and sessions use short-lived tokens with HttpOnly and Secure cookies, expiring after ten minutes of inactivity. Logout and password changes invalidate all active sessions.

## Data Protection and Privacy by Design

Data protection is built into the data model itself, following the Kenya Data Protection Act, 2019:

- **Encryption:** All traffic uses TLS 1.2 or higher. Personal data names, phone numbers, email addresses, consent records and backups are encrypted at rest and in transit.
- **Data minimisation:** The system collects only what its functions need. Device coordinates are used only to calculate nearby CSBs and are never stored.
- **Private by default:** New records and knowledge entries are private by default. Sharing seed records with GeRRI requires consent, and making a knowledge entry public requires a deliberate, confirmed step with a named approver.
- **Separation of data spaces:** Public knowledge is stored separately from private seed-record data, so publishing a guide never exposes an underlying holding.
- **Retention and deletion:** Security logs are retained for 12 months, backups follow a 30-day rolling cycle, and approved deletion requests replace identifying names on retained community records with neutral labels.
- **Cross-border transfers:** Handled where possible by hosting in-region; where processing happens outside Kenya, compliance with the Data Protection Act, 2019 is verified and documented.

## Audit Trail, Threats and Controls

The append-only `audit_record` table is the system's memory of who did what. The backend writes an audit row for every security-relevant action: sign-ins, failed sign-ins, invitation-code use, permission denials, sharing changes, exports, role changes and seed transfers. Rows are never updated or deleted, the application database role holds INSERT and SELECT rights only on this table, and logs never contain passwords, tokens, reset codes or message contents.

The main threats identified in our risk analysis, and the controls that answer them:

| Threat | Required control |
|---|---|
| **Unauthorized access** | Server side role and record-level authorisation; deny by default |
| **Data disclosure** | Encryption in transit and at rest, location masking, public/private separation |
| **Account compromise** | bcrypt hashing, account lockout, single-use reset codes, rate limiting, generic login errors |
| **Injection and XSS** | Server-side validation, parameterised queries, output encoding, Content Security Policy |
| **Malicious uploads** | File type and size validation; media stored outside executable code |
| **Record or flag tampering** | Append-only history, record level permissions, per-record change attribution |
| **Denial of Service** | Rate limiting, monitoring and alerts |
| **Data loss** | Daily encrypted backups stored separately, restore tested before the pilot and quarterly, recovery within 24 hours |

### Step 3b: Automated Contextual Filtering & Categorization Pipeline
Every Knowledge Hub text entry and media description is routed through a backend validation service layer to verify that the submission strictly pertains to communal seed banking or sustainable farming protocols. 

```text
 Inbound Post Text Description Payload (JSON String)
                   │
                   ▼
 [API Content Scanners / Substring Regex Filters]
                   │
                   ├──▶ Matches: agriculture, farming, seeds, sorghum, bean, crop...
                   │    │
                   │    └───▶ Valid: Route to Moderator Pending Queue ──▶ HTTP 201
                   │
                   └──▶ No Matching Contextual Keywords Found
                        │
                        └───▶ Rejected: Trigger Payload Exception Guard ──▶ HTTP 422
```

#### Core Keyword Ruleset Index
The backend system maps inbound content array queries against a strict relational regex configuration matrix:

| Monitored Pattern | Technical Validation Target | Action If Flagged |
|:---|:---|:---|
| `seeds`, `sorghum`, `maize`, `bean` | Specific crop variety context | Approves domain routing tag variables |
| `farming`, `agricultural`, `conservation` | Functional domain verification | Permits progression to local CSB review queue |
| `[Farmer Name]`, `[Location Coordinate]` | PII leakage tracking indices | Intercepts payload and locks visibility to Private |

#### API Router Validation Guard Blueprint
This validation logic executes on the FastAPI service boundary layer before writing entries to PostgreSQL:

```python
from fastapi import HTTPException, status
import re

AGRICULTURE_KEYWORDS = re.compile(
    r"\b(agriculture|agricultural|farming|seeds?|sorghum|bean|crop|conservation|cultivation|harvest)\b", 
    re.IGNORECASE
)

def validate_hub_content_context(text_payload: str) -> bool:
    """
    Validates that inbound Knowledge Hub posts strictly contain domain-relevant
    agricultural context before allowing database persistence.
    """
    if not AGRICULTURE_KEYWORDS.search(text_payload):
        raise HTTPException(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            detail="Submission rejected: Content must directly relate to agricultural or seed conservation topics."
        )
    return True
```


Error handling supports the same goal: users receive short, specific messages, and responses never expose database errors, file paths or software versions. Secrets and API keys live only in environment variables on the backend; debug mode and default accounts are disabled in production; and development, testing and production environments are separated.

Security is verified, not assumed. Before deployment the team completes source code review, dependency and static/dynamic security scanning, API security testing, privacy review, SBOM generation, offline and synchronisation testing, and backup-restore testing. Together with the 2021 Protocol for Collaboration's Prior Informed Consent and Community Data Sharing Agreements, these controls ensure that community seed information stays under community control at every layer of the system.
